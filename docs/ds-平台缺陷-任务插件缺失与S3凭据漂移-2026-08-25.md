# DS 服务两个平台级缺陷：任务插件缺失 与 S3 凭据漂移

> 发现于 2026-08-25，在五节点沙箱（`ddh-01`~`ddh-05`）验证「DS 工作流可视化」需求时踩到。
> 两条都不是本次需求引入的，而是**平台分发的 DS 服务本身的问题**，任何一次全新安装都会复现。
> 沙箱已做临时处置（见第 3 节），**平台侧尚未修**。

## 1. 缺陷一：分发的 DS 3.4.1 包**缺全部任务插件**

### 现象

通过 DS Open API 创建任何工作流定义都失败：

```
POST /dolphinscheduler/projects/{projectCode}/workflow-definition
→ {"code":10001,"msg":"request parameter {0} is not valid"}
```

**报错文案完全指错方向**——它看起来像参数拼错了，真因藏在 `api-server` 日志里：

```
java.lang.IllegalArgumentException: Cannot find TaskChannel for : SHELL
    at org.apache.dolphinscheduler.plugin.task.api.TaskPluginManager.getTaskChannel(TaskPluginManager.java:67)
    at org.apache.dolphinscheduler.plugin.task.api.TaskPluginManager.parseTaskParameters(TaskPluginManager.java:95)
    at ...WorkflowDefinitionServiceImpl.generateTaskDefinitionList(WorkflowDefinitionServiceImpl.java:438)
```

### 根因

DS 的任务类型通过 SPI 注册，每种类型一个独立 jar。平台分发的
`apache-dolphinscheduler-3.4.1-bin.tar.gz`（解压后 **405 MB**）里**一个都没有**：

| 检查项 | 实测 |
|---|---|
| `api-server/libs` jar 总数 | 420，其中 task 相关**只有** `dolphinscheduler-task-api`、`dolphinscheduler-task-executor` |
| `worker-server/libs` jar 总数 | 348，同上 |
| 全部 jar 中的 `*TaskChannelFactory` 实现 | 搜不到 `ShellTaskChannelFactory` / `SparkTaskChannelFactory` 等任何一个 |
| `dolphinscheduler-task-api` 的 SPI 文件 | `META-INF/services/…TaskChannelFactory` 里**只注册了 5 个 logic task**（Conditions / Dependent / LogicFake / SubWorkflow / Switch） |
| 安装包 `plugins/` 目录 | 只有 `storage-plugins/dolphinscheduler-storage-s3-3.4.1-shade.jar` |

### 影响

**平台装出来的 DS 只能创建 logic 类任务**（条件分支、依赖、子工作流、Switch）。
Shell / Spark / Flink / SQL / Python / HTTP 等**所有真正干活的任务类型，在"创建工作流定义"这一步就被拒**
——不是运行失败，是定义都存不进库。也就是说 **DS 在平台上目前不可用**。

### 建议修复

把官方 artifact 补进分发包的 `api-server/libs`、`master-server/libs`、`worker-server/libs`
（三处都要，api 侧做参数校验、worker 侧做执行）。Maven Central 上齐全：

```
org.apache.dolphinscheduler:dolphinscheduler-task-shell:3.4.1          (12 KB)
org.apache.dolphinscheduler:dolphinscheduler-task-spark:3.4.1          (20 KB)
org.apache.dolphinscheduler:dolphinscheduler-task-flink:3.4.1          (24 KB)
org.apache.dolphinscheduler:dolphinscheduler-task-flink-stream:3.4.1   (12 KB)
org.apache.dolphinscheduler:dolphinscheduler-task-sql:3.4.1            (19 KB)
org.apache.dolphinscheduler:dolphinscheduler-task-python:3.4.1         (13 KB)
org.apache.dolphinscheduler:dolphinscheduler-task-http:3.4.1           (23 KB)
```

体积都很小（依赖走 libs 里已有的），按平台实际要支持的任务类型取舍即可。
需要同步决定的是：**这批 jar 是打进 tar 包，还是像 OpenLineage / Paimon 那样走 Nexus 分发**。

## 2. 缺陷二：DS 的 S3 凭据与 RustFS 实际不符（**重启才暴露**）

### 现象

补完插件重启 `ApiServer`，服务**起不来**：

```
BeanCreationException: Error creating bean with name 'storageOperate'
  defined in org.apache.dolphinscheduler.plugin.storage.api.StorageConfiguration
Caused by: com.amazonaws.services.s3.model.AmazonS3Exception:
  The request signature we calculated does not match the signature you provided.
  Check your key and signing method.
    at ...S3StorageOperator.exceptionWhenBucketNameNotExists(S3StorageOperator.java:209)
```

### 根因

DS 的 `common.properties` 配置 `resource.storage.type=S3`，指向 RustFS
（`aws.s3.endpoint=http://<rustfs>:9040`）。实测比对：

| 项 | 结果 |
|---|---|
| `aws.s3.access.key.id` | 与 RustFS 一致 |
| bucket `dolphinscheduler` | 在 RustFS 上**存在** |
| **`aws.s3.access.key.secret`** | **与 RustFS 进程实际的 `--secret-key` 不一致** |

**这个错误配置存在已久，只是一直没被发现**：S3 客户端只在服务启动时初始化一次，
ApiServer 自上次启动后从未重启，于是错误被运行中的旧进程掩盖着。
这是典型的"**重启才暴露的配置漂移**"——任何"一直好好的"服务，其配置正确性只有在重启那一刻才真正被验证。

### 影响

DS 任一角色（api / master / worker / alert）**只要重启就起不来**。
在此之前一切正常，因此这个雷会在最不合适的时候引爆（扩容、打补丁、机器重启）。

### 建议修复

在 `package/raw/meta/datacluster-physical/DS/service_ddl.json` 侧修，而不是手工改节点上的文件——
否则平台下次下发配置会把手工修复覆盖回去。更稳妥的做法是让 DS 的 S3 参数**引用对象存储服务的凭据**
（像其它跨服务占位符那样），而不是在 DS 自己的 DDL 里另存一份，从根上消除两处取值漂移的可能。

## 3. 沙箱已做的临时处置（仅沙箱，平台侧仍未修）

所有改动都留了 `.bak-*` 备份。

| 位置 | 改动 |
|---|---|
| `ddh-02`：`ds/{api,master}-server/libs/` | 补 5 个官方 task 插件 jar（shell / spark / flink / flink-stream / sql） |
| `ddh-03/04/05`：`ds/worker-server/libs/` | 同上 |
| `ddh-02`：`ds/{api,master,alert}-server/conf/common.properties` | `aws.s3.access.key.secret` 改为 RustFS 实际值 |
| `ddh-03/04/05`：`ds/worker-server/conf/common.properties` | 同上 |

处置后：ApiServer 正常启动（29 秒），工作流可创建、可上线、可执行，Shell 与 Spark 两种任务均跑通。

## 4. 连带记录：另外两个不是缺陷、但不知道就会卡住的点

1. **DS 3.4 新增默认租户门禁**：租户名为 `default` 时，worker 必须在 `application.yaml` 里配
   `tenant.default-tenant-enabled: true`，否则任务一到 worker 就 `FAILURE`，日志为
   `The tenantCode is default, please enable TenantConfig#isDefaultTenantEnabled`。
2. **`dolphinscheduler-daemon.sh start` 会用 `bin/env/dolphinscheduler_env.sh` 覆盖各服务 `conf/` 下的同名文件**。
   给任务配环境变量（`SPARK_HOME`、`FLINK_HOME` 等）必须改 `bin/env/` 那一份，改 `conf/` 下的会被一次重启抹掉。
   另外该文件默认只有 `SPARK_HOME1` / `SPARK_HOME2` 且指向不存在的 `/opt/soft/spark1|spark2`，
   而 DS 3.4.1 的 Spark 插件用的是 `${SPARK_HOME}/bin/spark-sql`——**变量名对不上**，必须显式补 `SPARK_HOME`。
