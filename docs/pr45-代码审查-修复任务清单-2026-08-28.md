### 1. ConfigForm 隐藏字段过滤破坏安装向导
- **文件**：`datasophon-ui-v2/src/pages/Cluster/ServiceInstance/Setting/ConfigForm.tsx:285`（配套 `configTransform.ts:106,132`）
- **verdict**：CONFIRMED
- **问题**：新增的 `!item.hidden` 渲染过滤器 + `!val.hidden` 提交过滤器修复了 Settings 页字段泄露，但 `ConfigForm` 同时被安装向导（`AddService/StepConfig.tsx`）复用，未区分 `configurableInWizard`。
- **影响面**：HDFS-HA（`dfs.namenode.rpc-address.*.nn1/nn2`）、Kafka（`kafkaHost`/`kafkaRealm`）、Hive（`hive.server2.thrift.bind.host/port`）、ES（`heapSize`/`otelJavaagentPath`）— 这些字段同时标了 `hidden:true` 和 `configurableInWizard:true`。安装向导中会被静默隐藏，保存时值被丢弃，最终落到未解析的 DDL 默认值。
- **建议修复**：给 `ConfigForm` 增加 `context: 'settings' | 'wizard'` prop，向导场景下过滤条件改为 `!item.hidden || item.configurableInWizard`（`configTransform.ts` 提交过滤同步处理）。
- **验证方式**：分别走一遍 HDFS-HA / Kafka / Hive / ES 的安装向导，确认上述字段在向导中可见且提交后值正确落库；再走一遍 Settings 页确认原有泄露问题仍被修复。
- **✅ 修复记录**：`ConfigForm.tsx` 新增 `context` prop（默认 `'settings'`），`configTransform.ts` 的 `invokeHandleTemplateData`/`invokeFormatTemplateData` 新增 `isWizard` 参数（默认 `false`，向后兼容）；`service.d.ts` 补上前端此前缺失的 `configurableInWizard` 字段类型（后端 `ServiceConfig.java` 早已有该字段，只是没透传到前端类型）；`StepConfig.tsx`/`AddServiceModal.tsx` 接入 `true`/`"wizard"`。补充单测 `configTransform.test.ts`，Biome + tsc 全绿。**尚未做浏览器实机验证**，建议合并前手动过一遍 HDFS-HA/Kafka/Hive/ES 安装向导确认字段可见且能保存。

### 2. STREAM 任务瞬时零行查询被误判为未绑定
- **文件**：`datasophon-api/src/main/java/com/datasophon/api/ds/DsStreamMetricsProvider.java:106`
- **verdict**：CONFIRMED
- **问题**：`hasHistoricalBinding()` 只在 `taskEnded` 分支内被调用；任务仍在 RUNNING 时，若某次查询恰好零行匹配（OTel 采集短暂空档 / Flink 作业重启导致），`selected == null` 会直接抛 `NotBoundException`，不会回退检查历史绑定。
- **影响面**：健康运行中的流作业会在 UI 上间歇性闪现"未绑定"。
- **建议修复**：把 `hasHistoricalBinding()` 的回退检查提到 `selected == null` 分支统一处理，不再限定 `taskEnded`。
- **验证方式**：本地模拟一次 OTel 查询返回空结果（mock repository 返回空列表），断言 RUNNING 状态下仍能回退到历史绑定而非抛异常；跑 `DsStreamMetricsProvider` 相关单测。
- **✅ 修复记录**：`hasHistoricalBinding()` 检查提到 `selected == null` 分支统一处理；曾绑定过但 RUNNING 时零行匹配，改为抛 `IllegalStateException`（与本文件已有的"RUNNING 但瞬时无 rate"分支同一语义），上游 `DsWorkflowServiceImpl` 会归为 `metricsError=LOOKUP_FAILED` 而非误报 `NOT_BOUND`；`taskEnded=true` 时行为不变，仍抛 `JobEndedException`。新增单测 `doesNotReportNotBoundForRunningTaskWithHistoricalBindingButTransientEmptyQuery`，`DsTaskMetricsServiceTest` 9/9 全绿。

### 3. DAG 查询未使用为其新建的隔离线程池
- **文件**：`datasophon-api/src/main/java/com/datasophon/api/service/impl/ds/DsWorkflowServiceImpl.java:143`
- **verdict**：CONFIRMED
- **问题**：`dag()` 里两次 DS-ApiServer HTTP 调用仍派发到共享的 `masterExecutor`，而不是本 PR 同时引入、专为此类慢速外部 I/O 设计的 `dsMetricsExecutor`。
- **影响面**：`masterExecutor` 同时被 `MasterScheduledService`/`HostCheckService` 用于周期性集群健康巡检；`DsDagPage.tsx` 每 15 秒自动轮询一次，多个并发打开的 DAG 标签页会占满 `masterExecutor` 线程，拖慢无关的集群健康检查 —— 正是 PR 自己注释里说要规避的风险，只是没有实际接上。
- **建议修复**：把这两处 HTTP 调用改派到 `dsMetricsExecutor`。
- **验证方式**：确认 `dsMetricsExecutor` 的线程池配置能覆盖当前并发场景；跑相关集成测试确认 DAG 查询功能不受影响。
- **✅ 修复记录**：`dag()` 里两处 `client.get()` 改用 `dsMetricsExecutor`；`masterExecutor` 字段在改完后于本类中完全无引用，按"自己改动产生的孤儿要清理"一并移除该字段与构造参数（`@Qualifier("masterExecutor")` 参数），同步把 `DsWorkflowServiceTest` 的构造调用从 5 参数改为 4 参数。`./mvnw ... -Dtest=DsWorkflowServiceTest,DsTaskMetricsServiceTest test` 14/14 全绿；`clean test-compile` 全量编译 703+109 个源文件通过，Checkstyle 0 违规。

### 5. 分组查询的 `ts` 列语义静默改变
- **文件**：`datasophon-api/src/main/java/com/datasophon/api/observability/OtelMetricsQueryService.java:634`
- **verdict**：PLAUSIBLE
- **问题**：`buildInstantAggSql` 在 `groupByKeys` 非空时，`ts` 列从恒定的 `UNIX_TIMESTAMP(NOW())`（查询时间）改成了 `MAX(sample_ts)`（最后采样时间）。这是平台级共享构建器，不止服务于 DS 一处。
- **影响面**：当前唯一已识别调用方 `LineageJobMetricsService` 忽略 `ts` 列，暂时无害；但语义变化未经测试覆盖，是留给下一个按 key 分组且读取 `ts` 的调用方的潜在陷阱。
- **建议修复**：至少加一条注释说明该语义差异，或者给 `ts` 起个更明确的名字（如区分 `query_ts` / `last_sample_ts`）防止未来误用；如可能，补一个针对分组场景 `ts` 语义的单测。
- **✅ 修复记录**：在 `sampledAt` 赋值上方加注释，明确分组查询下 `ts` = 组内最后采样时刻（`MAX(sample_ts)`）而非查询时刻，提醒未来按 key 分组又读取 `ts` 的调用方注意区分。未改字段名/签名，避免影响现有唯一调用方 `LineageJobMetricsService`（其本就忽略 `ts` 列）。

### 6. `requiresRestart` 硬编码服务名分支
- **文件**：`datasophon-api/src/main/java/com/datasophon/api/service/impl/ServiceInstallServiceImpl.java:255`
- **verdict**：PLAUSIBLE
- **问题**：被所有服务共用的通用 `saveServiceConfig` 路径里，用字面量 `"DS".equals(serviceName)` 特判来跳过"配置未变化不标记重启"逻辑。
- **影响面**：架构债 —— 下一个需要同样"仅改配置、无需重启"优化的服务，只能在这里重复堆一个 if 分支，而不是通过 DDL 按参数声明 `requiresRestart: false`。
- **建议修复**：评估把该能力提升为 DDL 层的参数级属性（`requiresRestart: false`），移除硬编码分支；若短期工作量过大，至少加注释标注这是临时方案、TODO 指向 DDL 化。
- **✅ 修复记录**：短期未做 DDL 化改造（工作量超出本轮修复范围，涉及 DDL schema + 解析层改动），按建议的兜底方案在 `requiresRestart()` 方法上补充 TODO 注释，明确标注这是临时方案、指向未来的 DDL 化方向，防止后续贡献者误以为这是长期设计。

### 7. 平台托管配置清单在两处重复维护
- **文件**：`datasophon-api/src/main/java/com/datasophon/api/utils/ServiceConfigUtils.java:172`（配套 `DdlMetaServiceImpl.java:396`）
- **verdict**：PLAUSIBLE
- **问题**：`if (!DS_SERVICE_NAME.equals(serviceName)) return;` 的平台托管配置特判逻辑在两个文件里各自维护一份"哪些 key 是平台托管"的硬编码集合（一个是 `Map`，一个是 `Set`）。
- **影响面**：两份清单可能悄悄失步 —— 在一处新增/改名平台托管的 S3/凭据 key 而未同步另一处，会导致该 key 在配置合并路径被托管、但在 DDL 刷新路径未被托管（或反之）。
- **建议修复**：抽取成单一 SSOT（常量类或配置文件），两处都引用它。
- **✅ 修复记录**：新增 `com.datasophon.api.ds.DsManagedConfig`（`SERVICE_NAME` + `OBJECT_STORAGE_CREDENTIALS: Map<String,String>`）作为单一 SSOT；`ServiceConfigUtils.applyPlatformManagedConfigValues` 与 `DdlMetaServiceImpl.refreshPlatformManagedConfigValues` 均改为引用该类，删除各自原有的 `DS_SERVICE_NAME` / `DS_MANAGED_OBJECT_STORAGE_CREDENTIALS`（`Map` 与 `Set` 两种形态统一为 `Map`，`Set` 场景用 `.containsKey()` 替代 `.contains()`）。

### 8. DsApiClient 每次调用都重复解析 token 与 endpoint
- **文件**：`datasophon-api/src/main/java/com/datasophon/api/ds/DsApiClient.java:71`
- **verdict**：PLAUSIBLE
- **问题**：每次 `DsApiClient.get()` 都重新执行 `DsConfigService.apiToken()`（DB+DDL 合并）与 `DsEndpointResolver.resolve()`（角色列表+主机 DB 查询），没有任何缓存。
- **影响面**：`DsDagPage` 每 15 秒轮询一次 `/dag`，`dag()` 本身又并发发起 2 次 `client.get()` 调用，因此每次轮询都要重复 4 次数据库往返去解析在页面生命周期内其实稳定不变的值（token、ApiServer 主机）—— 随并发打开的 DAG 标签页数量线性增长的可避免数据库负载。
- **建议修复**：给 token 和 endpoint 解析结果加短 TTL 缓存（例如 30-60 秒，覆盖轮询间隔即可，同时保证配置变更后能较快生效）。
- **✅ 修复记录**：`DsApiClient` 新增 `ConcurrentHashMap<Integer, CachedResolution>`，按 `clusterId` 缓存 `token` + `endpoint` 二元组，TTL 30 秒（覆盖 `DsDagPage` 15s 轮询周期的约 2 轮）；`get()` 改为先查 `resolution(clusterId)`，命中且未过期直接复用，否则重新解析并写回缓存。未引入定时清理，缓存按 clusterId 数量有界（集群数不会无限增长），可接受。

### 10. `shortDatasetName` 对含扩展名的数据集名处理过于宽泛
- **文件**：`datasophon-ui-v2/src/pages/Cluster/ServiceInstance/DsWorkflow/formatters.ts:39`
- **verdict**：PLAUSIBLE
- **问题**：函数同时按 `/` 和 `.` 切分，当前唯一调用点（`DsDagGraph.tsx`，OpenLineage 的 `db.table` 命名）能正常工作，但函数对任意 BATCH 输出名都通用；未来若出现类似 `orders_2026.parquet` 这种基于文件/湖仓的输出名，会被压缩成仅剩 `parquet`。
- **建议修复**：非阻塞项 —— 若近期无此类输出名的实际场景，可暂不处理，仅记录在案；如需修复，改为只按最后一个 `/` 切分，不再切 `.`。
- **⏸️ 处理结果**：与用户确认后维持现状，不改。核实后发现审查建议的"只切 `/` 不切 `.`"方案会破坏当前唯一调用点正常工作的场景 —— 后端 `output.name` 来自 OpenLineage 数据集名，JDBC 类数据集格式是 `db.table`（不含 `/`），按建议方案会不再切分、直接展示完整 `db.table`，与"当前调用点能正常工作"的前提矛盾。近期无文件类输出名的实际场景，暂不处理，仅记录在案。
